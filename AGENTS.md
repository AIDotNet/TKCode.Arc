# TKCode.Arc agent guide

TKCode.Arc is an Arc-style (uiarc.dev) component library for Avalonia 12 (the version is `AvaloniaVersion` in `build/Versions.props`). Every package depends only on Avalonia and the in-house MIT `TKCode.Arc.Foundation` (token runtime, theme manager, package registration, localization; design/architecture/foundation.md); the exceptions are `TKCode.Arc.Markdown` and `TKCode.Arc.Highlighting`, which bring StreamMark (and through it Markdig and TextMate) so that `TKCode.Arc` does not (design/decisions/0050-markdown-and-highlighting-packages.md). StreamMark itself lives in this repository (`TKCode.Arc.StreamMark*`, below).
Design source of truth: `design/` (start at `design/overview.md`). It is the maintainers' local working area and is not in the repository (`.gitignore`, since commit 4092a675): a fresh clone has no `design/`, and the `design/...` paths below and in the CHANGELOG point into it. Without it, this file, the XML docs and the code are the reference; the rules below stand on their own.

## Layout

- `src/TKCode.Arc.Foundation` (+ `TKCode.Arc.Foundation.Generators`, shipped as its analyzer): token and theme runtime (`ArcThemeManager`, `ArcTheme`, presets), `AppBuilder.UseArc(...)` / `ArcBuilder`, language runtime (`TKCode.Arc.Localization`), generators for tokens, theme files and `Localization/*.xlf`.
- `src/TKCode.Arc.Core`: ArcDesign tokens, palette, motion engine (`TKCode.Arc.Motion`), shared primitives (`TKCode.Arc.Primitives`), Lucide glyphs.
- `src/TKCode.Arc`: controls, organized as `<Category>/<Component>/` (category = Arc sidebar group).
- `src/TKCode.Arc.Markdown` (`Markdown`, `ChatThread`, `ChatComposer`; `UseArcMarkdown()`) and `src/TKCode.Arc.Highlighting` (TextMate highlighting for `CodeBlock`, the rich text editor and Markdown, installed by `UseArcHighlighting()`; its `ArcHighlightLanguages` targets trim unused grammars): keep StreamMark, Markdig and TextMate out of `TKCode.Arc`. Code there highlights only through the internal `ICodeSyntaxHighlighter` in `Tables/CodeBlock/CodeBlockSyntax.cs`.
- `src/TKCode.Arc.StreamMark` (streaming Markdown engine and views: `Core/` = `StreamMark.Core.*`, `Avalonia/` = `StreamMark.Avalonia.*`) and its plugin packages `TKCode.Arc.StreamMark.TextMate`, `.RaTeX` (native `libratex_ffi`, pinned in `native/ratex/ratex-upstream.json`, built by `tools/streammark/build-ratex.sh`) and `.Mermaid`: StreamMark, moved in from its own repository (AtomUICommunity/StreamMark at 0.1.2) and published with Arc. Tests in `tests/TKCode.Arc.StreamMark.Tests`, the AOT smoke Gallery and benchmarks in `tools/streammark/`. Its own rules, commands, code map and memory are in `docs/streammark/` (start at `docs/streammark/agent-guide.md`); read it before changing these packages.
- `src/TKCode.Arc.Graphics3D` (3D engine, pure .NET: no Avalonia or Foundation reference; namespace `TKCode.Arc.Graphics3D`), `src/TKCode.Arc.Graphics3D.WebGpu` (`WgpuDevice`: the engine's second backend, over wgpu-native, which the application supplies; it also runs compute shaders), `src/TKCode.Arc.Graphics3D.Controls` (`Viewport3D`, `ModelViewer`; `UseArcGraphics3D()`) and `src/TKCode.Arc.Graphics3D.Browser` (the viewport's WebGL 2 context in a browser app; `UseArcGraphics3DBrowser()`): preview packages that ship with `ArcVersion` like every other package, under their own rules, see 'Graphics3D' below. Design: `design/architecture/graphics3d.md`, `design/decisions/0051-graphics3d-package.md`. `tools/graphics3d/Probe` runs a `Viewport3D` in a real window and writes the platform's device report.
- `tests/`: one project per package, each with a headless app that enables only the packages it tests: `TKCode.Arc.Core.Tests` (pure), `TKCode.Arc.StreamMark.Tests` (StreamMark and its plugins; the math tests need `tools/streammark/build-ratex.sh` first), `TKCode.Arc.Tests` (the controls of `TKCode.Arc`, Markdown and Highlighting), `TKCode.Arc.Blocks.Tests`, `TKCode.Arc.Special.Tests`, `TKCode.Arc.Extras.Tests` (AdvancedCharts, Dock, Workflow, Terminal, Video, Pdf, the Graphics3D controls), `TKCode.Arc.Integration.Tests` (needs every package: token baselines, Pixel and Corners, template contracts), `TKCode.Arc.Foundation.Tests` (runtime + generator snapshots), `TKCode.Arc.BaseTheme.Tests` (base theme in an app with no other theme), `TKCode.Arc.Mobile.Tests`, `TKCode.Arc.A2UI.Tests`, `TKCode.Arc.Graphics3D.Tests` (the engine: pure tests, and render tests that draw for real in an off-screen OpenGL context and skip themselves where there is none), and `Video.Native` / `Pdf.Native` (need the native libraries). Helpers they share are linked source in `tests/Shared/`. The tests that use gallery demos are in ArcGallery; `tests/Baselines/` holds the token and preset snapshots.
- The gallery and documentation site is its own repository, [AIDotNet/ArcGallery](https://github.com/AIDotNet/ArcGallery), checked out next to this one as `../ArcGallery` (its projects find this checkout through `ArcRoot`; section 'Gallery' below). It holds the shell, the docs pages (`Docs/<Category>/<Component>/<lang>.md`), the demos, the screenshots, the generators that build the API tables from this repository's XML docs, the desktop and browser hosts, `tools/docshots` and the tests that go through the demos (`tests/TKCode.Arc.Gallery.Tests`). Design notes: `design/engineering/gallery-app.md`.
- `tools/lucide/generate_lucide.py`: regenerates Lucide glyph geometry: Core's `ArcIcons.g.cs`, the `LucideIconKind` enum of `TKCode.Arc.Icons.Lucide` and the path data of `TKCode.Arc.Icons.Lucide.Generators` (`LucidePaths.txt`). That generator ships in the Icons.Lucide package and compiles only the icons a project uses into it (C#, XAML, `<LucideIcon Include="..." />` items, or `LucideIconsIncludeAll`); repository projects opt in with `ArcLucideGenerator=true`.

## Implementation handbook

Read `design/engineering/implementation-guide.md` before writing a component: file layout, token rules, theme and motion patterns, the Core primitive catalog, performance and API rules, tests and known pitfalls.

## Non-negotiable rules

- Controls derive from Avalonia base types; only public Avalonia APIs are used. No AtomUI code or packages, and none of its source is consulted (clean room; design/decisions/0031-replace-atomui.md).
- Class names have no prefix; flat namespace `TKCode.Arc`; xmlns `https://github.com/AIDotNet/TKCode.Arc`. `TKCode.Arc.Mobile` is the exception: namespace `TKCode.Arc.Mobile`, xmlns `https://github.com/AIDotNet/TKCode.Arc.Mobile` (prefix `arcm`), and a few of its types share a desktop name (`Button`, `ButtonVariant`, `Checkbox`, `Dialog`, `RadioCard`, `RadioCardOption`, `RadioCards`, `Switch`, `Toast`; pinned by `MobileClassNameTests`, #152). New Mobile types do not reuse desktop names; a C# file that imports both namespaces aliases one side (`using MobileButton = TKCode.Arc.Mobile.Button;`).
- `TKCode.Arc.Terminal` is a standalone terminal library published with Arc (#150, ADR 0052): it depends on Avalonia alone, keeps its `TKCode.Terminal.*` namespaces, needs no `UseArc` entry, and takes its colors from the terminal core's palette (the host sets it), so the token, theme and registration rules below do not apply to it. Its default font starts with Geist Mono.
- The `TKCode.Arc.StreamMark*` packages are standalone libraries published with Arc, like Terminal: they depend on Avalonia (plus Markdig, TextMate, Mermaider / Svg.Skia, the RaTeX native library) and never on Foundation, Core or the controls, keep their `StreamMark.*` namespaces, need no `UseArc` entry, and take their look from the `Md.*` resources a host maps (Arc's `Markdown` maps them onto tokens), so the token, theme and registration rules below do not apply to them. They keep StreamMark's stricter gate: trimming and AOT warnings are errors (build/ProjectDefaults.props). They follow the rest: braces, no reflection, PublicAPI files, CHANGELOG, the deprecation rule.
- Every public control has a `[ControlDesignToken]` `<Control>Token` in the same namespace with at least one property (ARCF003). Its identity (class name minus `Token`, or `[ControlDesignToken(Identity = "...")]`) is unique across all Arc packages, Mobile included (Mobile uses `MobileButton`, `MobileSwitch`, ...; design/engineering/reserved-token-names.md). Token property types are limited to those in foundation.md section 3.4 (ARCF001).
- Colors, radii, shadows and fonts come from `{arc:ArcDesignTokenResource ...}`; control tokens hold geometry and accent-independent derived colors only.
- Themes live in `<Component>/Themes/<Component>Theme.axaml` with `x:Class="<RootNamespace>.<FileName>" x:ClassModifier="internal"` (flat, e.g. `TKCode.Arc.ButtonTheme`, `TKCode.Arc.Mobile.PageTheme`; the generator supplies the class and loads the file on first use; ARCF010–014). A `ControlTheme` key is defined by one file only (ARCF013). Never create `*Themes.axaml` aggregates.
- Avalonia built-ins inside templates (`ScrollViewer`, `ScrollBar`, `ItemsControl`, `PathIcon`, `TextSelectionHandle`, popup hosts) get their theme from Core's base theme (`src/TKCode.Arc.Core/Theme/Base/`), which steps aside when the app uses Fluent or Simple. Other built-ins (e.g. `TextBox`) have no template: use the Arc control. Scroll bars auto-hide; set `ScrollViewer.AllowAutoHide="False"` to keep them.
- Theme changes go through `ArcTheme.Apply(t => ...)` / `ArcThemeManager.Apply`; never block on `ArcThemeManager.ApplyAsync` from the UI thread (its publish step needs the UI thread, so `.Wait()` / `.Result` deadlocks; await it or call `Apply`).
- A control that draws in `Render` (charts, text effects, per-frame motion) takes every color and size from its tokens or from brush properties, never hard-coded, because a new template does not change what it draws. The gallery's API tables say for each control whether it is templated or drawn (#154).
- Use Core's shared helpers instead of writing your own (#148): `ArcColor` (Lerp, LerpOklab, WithOpacity) for blending, `ArcFormatting` (Compact, Bytes, ToParts) for numbers and sizes, `ListKeyboardNavigator` for arrow-key lists, `DragTracker` / `DragRecognizer` / `VelocityTracker` for dragging, `Springs` / `MotionValue<T>` for springs. `DuplicateHelperTests` keeps allow-lists (`tests/TKCode.Arc.Tests/Architecture/Allowlists/`) of the files that still have their own copy. They only shrink: when you change one of those files, move it over and remove its line.
- Transitions are declared in ControlTheme setters under `^:motion-full` / `^:motion-reduced` (set `arc:ArcMotion.Tracks="True"`); code-driven motion uses `MotionValue<T>` and must say why ControlTheme cannot express it.
- Keep a source file to about 1200 lines: split a large control into `partial` files by concern (`Xxx.Input.cs`, `Xxx.Layout.cs`, `Xxx.Render.cs`, ...) and give each extra type its own file, when you next work on it (#153; `TreeSelect`, `Table`, `RichTextEditor` and `RichTextEditorSurface` show the shape). A guide, not a test.
- C# control-flow bodies always use braces. No reflection; AOT and trimming safe.
- Every Arc component needs gallery docs pages `Docs/<Category>/<Component>/{en-US,zh-CN,zh-TW}.md` in the ArcGallery repository (`../ArcGallery/gallery/TKCode.Arc.Gallery/`, checked by its `GalleryDocsTests`; design/engineering/gallery-app.md section 6.6), and its public properties and events need XML `<summary>` text here (they feed the API tables).
- Every new component or block gets the gallery's "New" badge: its catalog entry carries `AddedOn: "yyyy-MM-dd"` (the day it joins the gallery; the badge shows for `GalleryCatalog.NewWindowDays`). Arc components: the entry in ArcGallery's `Catalog/GalleryCatalog.g.cs` (keep it when regenerating); Extras, Special and Workflow: the entry in `GalleryCatalog.cs`; Blocks and Mobile: the `s_addedOn` table in `GalleryCatalog.cs` (checked by `GalleryNewBadgeTests`).
- Versions follow [Semantic Versioning](https://semver.org/): from 1.0.0 on, breaking API changes come only with a new major version. Record each release's changes and migration notes in `CHANGELOG.md`. A `-preview` suffix only allows changing members that no published package contains yet; for members that have shipped, preview included, the deprecation rule below applies.
- Every packable project lists its public API in `PublicAPI.Shipped.txt` (what released packages contain) and `PublicAPI.Unshipped.txt` (added since), checked by Microsoft.CodeAnalysis.PublicApiAnalyzers (#146): a public member that is in neither file (RS0016), or listed but gone (RS0017), fails the build. Add new members to `PublicAPI.Unshipped.txt` (`dotnet format analyzers <project> --diagnostics RS0016` writes them; for source-generated members, such as a new token property, copy the symbol from the RS0016 message). The stable release commit moves the Unshipped lines into Shipped. In Blocks and Special a block's root control, its item and data models, event args and token are public; the parts it is built from are internal unless an app needs to place them on their own.
- Public API is never removed or renamed in one step. The old member stays, marked `[Obsolete("Use X instead (deprecated in 1.Y.Z).")]` and forwarding to the new one, and is listed in `CHANGELOG.md` with its migration. It may be deleted only in a new major version, and only after it has carried `[Obsolete]` for at least two stable releases. This covers properties, events, methods, types, enum members and token names, and also changing a default, a parameter or what an event means. Code here and in ArcGallery moves to the new API in the same change and builds without CS0618, and a test keeps each obsolete member's forwarding working until it is removed.
- Item classes that a control lists (rows, options, actions: `SidebarItem`, `SegmentedOption`, ...) and controls with a selected state follow `design/engineering/implementation-guide.md` section 8: `IsEnabled` and `IsVisible` on every such item class (default `true`), `SelectionChanged` / `ValueChanged` for changes and `ItemInvoked` for "the user chose it".
- Releases go through one or more `X.Y.Z-preview.N` versions and end with a stable `X.Y.Z` of the same number; a new version number starts only after the previous one has shipped stable.
- Do not commit without an explicit request.

## Graphics3D

`TKCode.Arc.Graphics3D`, `TKCode.Arc.Graphics3D.WebGpu`, `TKCode.Arc.Graphics3D.Controls` and `TKCode.Arc.Graphics3D.Browser` are previews (design/decisions/0051-graphics3d-package.md). For these packages only:

- They ship with the main `ArcVersion` (build/Versions.props), with no version line of their own; their API stays preview-grade (below) even in a stable release.
- Their public API may change or be removed between previews without `[Obsolete]`; record each change in `CHANGELOG.md` under Graphics3D. All set `<ArcPublicApi>false</ArcPublicApi>`.
- No stable Arc package may reference them (a stable package cannot depend on a prerelease); they may reference stable packages.
- Engine types live in `TKCode.Arc.Graphics3D` (`.Shading`, `.Rhi`), not in the flat `TKCode.Arc` namespace, and the engine has no `UseArcXxx` entry; the controls stay in `TKCode.Arc` and follow every control rule (token, gallery docs, XML summaries).
- three.js (MIT) may be consulted for the engine, and for the decoders the formats' own reference code (Draco and Basis Universal, Apache-2.0; meshoptimizer, MIT; Zstandard's educational decoder, BSD); AtomUI still may not. Keep `THIRD-PARTY-NOTICES.md` current.
- `GlApi` calls OpenGL through function pointers. Every signature shape it uses has a delegate in `Rhi/OpenGL/GlSignatures.cs`, kept by a `DynamicDependency` on `GlApi`'s constructor: the WebAssembly build makes its interpreter-to-native trampolines from those, and a call through a shape without one ends the program in the browser. `GlSignatureTests` says which is missing.
- Materials are node graphs (`Sl`); engine shader code belongs in `Shading/ShaderLibrary.cs` and renderer code talks to `GraphicsDevice` only, never to OpenGL directly.
- On Linux the render tests use EGL with OpenGL ES 3 and need no display (Mesa: `libegl1 libgles2 libgl1-mesa-dri`; they skip themselves without it), so a container is enough to check Linux from another system. The Probe runs there under `xvfb-run`: `--x11=glx` or `--x11=egl` make Avalonia accept Mesa's software OpenGL (it refuses llvmpipe by default and then composites in software, where the viewport falls back to a bitmap), `--software` forces that fallback, and `--screenshot` saves what the X server shows (needs ImageMagick).
- The loader tests that need real model files (`SampleAssetTests`: meshopt, Draco, KTX2) skip themselves unless `TKCODE_ARC_GLTF_SAMPLES` names a folder with them; the repository carries no model files. Each test's comment says which public sample it wants and where it goes. Run them after changing a decoder.
- After changing the renderer or the shader library, run the render tests and look at the pictures under `artifacts/graphics3d/`: the assertions check a few pixels, not whether the lighting is right. Run them again with `TKCODE_ARC_RENDER_THREAD=1` (through `ThreadedGraphicsDevice`), with `TKCODE_ARC_WGPU=<path of libwgpu_native>` (the WebGPU backend; the library is a wgpu-native release and is not in the repository, so CI does not run this), and a second time on OpenGL ES 3.0 (the dialect Windows uses) with `TKCODE_ARC_ANGLE=<directory with ANGLE's libEGL and libGLESv2>`; any Chromium or Electron application ships those.

## Verify

Do not run the full test suites locally (the headless projects take minutes each, and much longer when several builds share the machine); CI runs every test project as its own job. Build what you touched and run only the tests for the code you changed, in the project of its package:

```bash
dotnet build src/TKCode.Arc -c Debug                    # or the package you changed
dotnet test tests/TKCode.Arc.Tests --filter "FullyQualifiedName~<Component>Tests"   # or Blocks.Tests, Special.Tests, Extras.Tests, ...
```

## Gallery

A component change that shows in the gallery (docs, demos, catalog, screenshots) is a second change in `../ArcGallery`, with its own build and tests (see its `AGENTS.md`):

```bash
cd ../ArcGallery
dotnet build gallery/TKCode.Arc.Gallery.Desktop         # no GDOC warnings
dotnet test tests/TKCode.Arc.Gallery.Tests --filter "FullyQualifiedName~GalleryDocsTests|FullyQualifiedName~GalleryDemosTests|FullyQualifiedName~GalleryNewBadgeTests|FullyQualifiedName~GallerySmokeTests.Catalog_Lists_All_Components"
```

The gallery builds against this checkout (and CI builds it against `main`), so an API change that breaks a demo has to land in both repositories; the libraries' `InternalsVisibleTo` list includes `TKCode.Arc.Gallery.Tests` for the tests that go through the demos.

Run a whole suite only when asked, or for a change that reaches across the library (Core, Foundation, generators, the base theme). A new test goes in the project of the package it tests; a test that needs several packages at once goes in `TKCode.Arc.Integration.Tests`, not into another project's test app.
