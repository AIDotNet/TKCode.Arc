# 0007 文档节奏：架构先行，组件规格按阶段编写

- 状态：已接受
- 日期：2026-10-20

## 背景

- 110 个组件的规模很大，一次性写完全部详细规格（属性、事件、模板部件、Token、动效、键盘、可访问性）前期投入很大。实现时，基础设施的结论还会变化，规格容易过时。
- 架构层决策（Token、动效、命名、注册）一旦确定，会影响所有组件；需要先写清楚并在 Phase 0 验证。

## 决策

1. 本期（文档期）交付：
   - 总览、术语、决策记录；
   - 架构文档（分层、集成、Token、动效、基元、浮层、字段、图标字体、可访问性、本地化）；
   - 110 个组件的总清单与 22 份大类 overview；
   - 规格模板、路线图与 Phase 0 spike、工程规范。
2. 每个组件的**详细规格**在其所属阶段开始前，按 [规格模板](../components/spec-template.md) 编写为 `design/components/<大类>/<组件>.md`。
   - 规格评审通过后才开始写代码（docs-before-code）。
3. 实现过程中发现设计需要改变时，先改文档（必要时新增 ADR），再改代码。

## 修订（实现阶段，2026-10-20）

- 用户指示整体启动全部组件的实现，并要求兼顾性能与易用的使用方式。
- 实际做法：
  - 不再逐个组件预先编写 `spec-template.md` 格式的规格文件；
  - 每个组件以 Arc 免费源码（MIT）为行为与视觉的依据，以大类 overview 中的条目为范围说明，实现说明回写到对应的大类 overview；
  - 通用的实现约定、Core 基元目录、性能与易用性规则集中写在 [组件实现指南](../engineering/implementation-guide.md)，由它替代逐组件规格中重复的部分。
- 规格模板保留，供需要单独评审的复杂组件（例如富文本编辑器）使用。

## 备选方案

- **一次性写完全部 110 份详细规格**：前期工作量很大，到实现时容易过时。未选。
- **架构 + 前两期组件的详细规格**：比本方案多写约 10 份规格；但 Phase 0 的 spike 结果可能改变规格中的 API 形态，提前写收益有限。未选。

## 后果

- 正面：架构与范围一次讲清；组件规格基于已验证的基础设施编写，返工少。
- 负面：大类 overview 中的 API 只是草案，以组件规格为准。
- 配套：
  - [路线图](../roadmap/overview.md) 中每个阶段的进入条件包含"本阶段组件规格已评审"。
  - [文档校验](../engineering/docs-verification.md) 检查规格文件与总清单的一致性。
