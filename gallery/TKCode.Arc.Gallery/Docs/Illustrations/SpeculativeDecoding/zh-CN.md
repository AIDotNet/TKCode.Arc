## 何时使用

`SpeculativeDecoding` 说明为什么当小型草稿模型先行工作时，语言模型可以更快地给出答案。草稿通道每次提出几个 token，以虚线的“幽灵”标签块显示；目标通道在一次前向计算中核对所有这些 token，目标模型认可的猜测会进入答案。卡片把整个运行按轮播放一次，并保留一组累计得分：与仅用目标模型相比，答案快了多少倍，草稿被接受的比例，以及每次目标前向计算写出的 token 数。它是一个讲解插图，而不是解码器：其中的数字仅供示意。

- **关于延迟的模型与产品页面**：写着“响应最多快 2.5 倍”的页面可以展示时间花在哪里。读者能看到大型模型的每次前向计算都可以写出多个 token，而不是一个。
- **推理仪表板与发布说明**：用 `Rounds` 回放你自己服务器录制的运行，可以把某个真实请求的接受情况和每次前向计算的 token 数，与汇总成千上万次请求的指标放在一起对照。
- **讲解草稿长度的取舍**：滑块让读者尝试 2 到 8 个 token 的草稿。草稿越长，猜对时每次前向计算写出的 token 越多，但被接受的比例越小，因为第一次失误之后的内容都会被丢弃。使用内置示例时，加速比在 4 时达到峰值。
- **与普通解码比较**：比较开关会在同一时钟上并行一条第二线，其中目标模型每次前向计算只写一个 token，因此两种方法之间的差距是可以看见的，而不只是文字陈述。
- **课程与博客文章**：运行是确定的。相同的 token、种子和草稿长度总会得到相同的轮次，因此截图或提到“第 3 轮”的段落始终准确。

## 何时不用

- **向用户流式输出真实回答**：使用 `MarkdownStream` 或聊天组件。本卡片解释速度背后的机制，它并不会随文字到达而逐步显示文本。
- **Token 概率与备选项**：展示某个位置的候选项及其分数的卡片是另一回事。这里的草稿模型只会猜对或猜错，不携带任何概率。
- **在模型之间路由请求**：推测解码对每个请求都会同时运行两个模型。若要说明哪个模型响应哪个请求，请使用路由器的示意图。
- **单次前向计算内部发生的事**：注意力与专家路由低于本卡片的讲解层次。若要展示模型内部的路由，请使用 `MixtureOfExperts`。
- **实时性能监控**：统计数据是根据卡片上的运行计算的，而不是来自你的流量。若需要这类数据，请使用你自己测量结果的图表。

## 用法

卡片无需数据。在不设置任何内容时，它播放内置示例：一段 22 个 token 的维护通知，每次草拟 4 个 token，需要 6 次目标前向计算，最终比仅用目标模型快 2.6 倍。

```xml
<arc:SpeculativeDecoding />
```

`SpeculativeDecoding` 派生自 `Explainer`，后者是动画讲解插图的基类；`Explainer` 又派生自 Avalonia 的 `TemplatedControl`。基类提供故事时钟、播放与重新开始按钮及其名称、自动播放和实时区域；本控件负责描述通道、答案和计算过程。

### 你自己的答案

`Tokens` 接受目标模型写出的答案，每个 token 对应一个 `DecodeToken`。文本保留前导空格，与分词器的习惯一致（`" refund"`）；没有前导空格的 token（例如标点）会与前面的词连在一起。`Ease` 表示草稿猜中该 token 的可能性（0 到 1；未设置时使用 0.9），`Miss` 是草稿猜错时提出的内容。为数字、名称和生僻词设置较低的 ease，并给出可信的 miss；简短的功能词和标点保持较高的 ease。若页面需要，通道名称可以使用虚构的模型名。

<Demo name="OwnAnswer" />

`Seed` 决定哪些猜测成功。每次猜测从带种子的生成器中抽取一个数字，数字小于该 token 的 ease 时猜测成功；抽取在第一次失败时停止。调整种子直到运行讲述你想要的故事，然后保持不变：相同的种子、token 和草稿长度总会重放相同的轮次。`TokensSource` 则接受一个 token 序列，用于数据绑定。

### 录制的运行

`Rounds`（或 `RoundsSource`）回放你自己服务器录制的运行，而不是模拟一次运行。每个 `DecodeRound` 包含草稿提出的 token、目标从开头接受了其中的多少个，以及目标自己写出的 token：即对第一个被拒绝猜测的更正，或所有猜测都被接受时的奖励 token。答案由被接受的草稿与目标的 token 按顺序组成。草稿长度滑块会被隐藏，因为录制的轮次已经固定了草稿长度。

### 结构

1. **标题栏**：标题（`Title`，同时也是卡片的无障碍名称）、一行说明当前步骤的状态文字，以及播放／暂停和重新开始按钮。状态文字在窄卡片上会换行，并在那里预留两行，因此通道永远不会移动。
2. **草稿通道**（`DraftLabel`、`DraftDetail`）：代表小型模型的小圆点。每一轮，它的标签块会以草稿颜色的虚线“幽灵”标签块逐个出现，等待时带有轻微的闪光。
3. **目标通道**（`TargetLabel`、`TargetDetail`）：代表大型模型的大圆点。每个标签块下方有一个单元格，由目标的扫过动作从左到右填充。被保留的猜测会获得一个勾号；第一个被拒绝的猜测被划掉并标上叉号，旁边显示目标自己的 token；其后的猜测淡出。当所有猜测都被保留时，会多出一个带加号的单元格，显示目标的奖励 token。
4. **答案行**（“Output”，比较时为“Speculative”）：整句话从一开始就排版好，因此该行永远不会重新排版。token 落入各自的位置，每个都以写出它的模型颜色加下划线：被接受的猜测用草稿颜色，目标自己的 token 用目标颜色。前向计算次数位于名称下方，结束时会出现一个勾号。
5. **仅目标行**（`IsComparing`）：同一句话，在同一时钟上每次目标前向计算写出一个 token，并以目标颜色加下划线。
6. **统计数据**：加速比、草稿被接受的比例和每次前向计算的 token 数。第一轮结算之前显示一个破折号，此后每轮结束后滚动到累计值。
7. **控件**：草稿长度滑块（2 到 8）和比较开关。
8. **摘要**：运行结束时，两条通道旁边会各显示两行总计。

### 故事及其计算

每一轮都有三个步骤。使用默认值（每次前向计算 640 ms，草稿成本 0.1）时：

| 步骤 | 时长 | 发生的事 |
|---|---|---|
| 草稿 | k × 64 ms | 草稿每 64 ms 提出一个标签块，共提出 k 个。k 为草稿长度，但最多为剩余 token 数减一，因此目标始终写出最后一个 token。 |
| 验证 | 0.72 次前向计算（461 ms） | 扫过动作以 0.4 次前向计算（256 ms，与单元格数量无关）穿过全部 k 个单元格。每个单元格在扫过其中点时得到判定结果。 |
| 结算 | 0.28 次前向计算（179 ms） | 被保留的猜测与目标的 token 以 20 ms 的间隔飞入答案，各列淡出，统计数据滚动。 |

因此一轮会写出 a 个被接受的猜测加上目标自己的一个 token，花费一次前向计算加上草拟时间。统计数据由截至目前各轮的累计值得出：

- **“Speedup”** = tokens / (passes + draft cost × drafted)。草拟时间计入其中，因此多草拟并非没有代价。
- **“Drafts accepted”** = accepted / drafted，以整数百分比表示。
- **“Tokens per pass”** = tokens / passes。仅用目标模型时恰好为 1。

内置示例展示了读者应当记住的形状。加速比在草稿长度为 4 时升到最高，之后下降，而草稿被接受的比例则持续下降：

| 草稿长度 | 前向计算次数 | 草拟数 | 接受数 | 接受比例 | 加速比 |
|---|---|---|---|---|---|
| 2 | 10 | 19 | 12 | 63% | 1.8× |
| 3 | 8 | 21 | 14 | 67% | 2.2× |
| 4 | 6 | 24 | 16 | 67% | 2.6× |
| 5 | 6 | 29 | 16 | 55% | 2.5× |
| 6 | 6 | 33 | 16 | 48% | 2.4× |
| 8 | 6 | 39 | 16 | 41% | 2.2× |

`PlannedStats` 在运行被计划后立即给出整个运行的总计，`Stats` 给出截至目前已结算各轮的总计，`Completed` 则在推测线完成时报告总计。`DraftCost` 设置一个草稿 token 的成本（占一次前向计算的比例），它同时作用于屏幕显示和加速比；`PassDuration` 设置一次前向计算在屏幕上所占的时长。

### 与仅用目标模型比较

`IsComparing` 会打开仅目标行。它在与推测线相同的时钟上，于 (m − 1) 次前向计算加 0.72 次前向计算的时刻写出第 m 个 token，因此示例的 6 次前向计算之后，仅用目标模型只写出了 22 个 token 中的 8 个。推测线结束后，故事会继续运行，直到仅用目标的那条线也完成，状态文字会说明这一点。运行结束后再打开比较，会从那里接着计时，而不会重新开始运行。统计数据和 `Completed` 始终描述推测线。

### 播放

运行只播放一次：卡片第一次大部分可见时（`AutoPlay`）开始，结束时停止；`IsLooping` 会在几秒后再次播放。播放按钮会在停止的位置暂停和继续运行，播放结束后则从头开始。重新开始总是从头播放。`IsPlaying` 是双向的，`Play()`、`Pause()` 和 `Restart()` 在代码中完成相同的操作。`Speed` 缩放时钟；卡片上没有速度控件，也没有单步按钮。

更改草稿长度（通过滑块或 `DraftLength`）会重新计划运行，并从头播放。新的 token、轮次、种子、草稿成本或前向计算时长也是如此。与旧值相等的输入（例如内容相同的新列表）不会重新开始运行。

```xml
<arc:SpeculativeDecoding DraftLength="{Binding DraftLength}"
                         IsComparing="{Binding ShowsBaseline}" />
```

```csharp
decoder.Completed += (_, e) => status.Text = $"{e.Stats.Speedup:0.0}× faster in {e.Stats.Passes} passes";
decoder.DraftLength = 6;
decoder.Restart();
```

### 加载与错误

`Status` 描述录制运行背后的数据。在 `Loading` 状态下，通道变暗，状态文字显示加载指示器和闪烁的标签，控件被禁用，运行处于等待状态；状态变为 `Ready` 后自动播放才会开始。`Error` 会显示 `ErrorText`（或默认消息）并附带危险图标。只有当有人处理 `RetryRequested`，或设置了 `RetryCommand` 时，重试按钮才会出现在播放按钮旁边，因为一个没有作用的按钮比没有按钮更糟。

### 窄卡片

### 减弱动效

在减弱动效下，卡片不会自行开始，也不会直接跳到结尾：它停留在第一个状态，直到读者按下播放。运行仍有完全相同的各个节拍，但标签块出现时不滑动，扫过动作每次前进整个单元格，划线立即绘制，没有闪光，token 则直接出现在答案的位置，而不是飞过去。

### 内容指南

编写一段 15 到 30 个 token 的答案，它本身应当读起来通顺，并像真实模型遇到的那样混合容易和困难的 token：功能词和标点容易，数字、名称和关键名词困难。每次失误都应是同类的、合理的错误猜测（不同的数字、相近的词），而不是随机的词。通道名称保持通用，或使用明确虚构的名字；除非运行确实来自某个真实产品，否则不要使用其名称。

| 不要写 | 改为 |
|---|---|
| 一个 60 个 token 的句子 | 一两个 15 到 30 个 token 的短句 |
| 每个 token 的 ease 都是 0.5 | 容易的 token 约 0.95，困难的约 0.1 到 0.3 |
| 数字的 `Miss=" banana"` | 把 `" 25"` 的 `Miss` 设为 `" 30"` |
| 模拟运行上使用真实模型名 | “Draft model”和“Target model”，或虚构的名字 |
| 模拟运行旁的页面文字写“快 3 倍” | “在这个仅供示意的运行中，约快 2.6 倍” |

### 最佳实践

**推荐**

- 运行是模拟的时，请说明数字仅供示意；运行是录制的时，请说明它来自何处。
- 示例保持默认的草稿长度 4，这样第一次运行展示的是最佳加速比，而滑块则能在两个方向上展示取舍。
- 对于要引用的数字，使用 `Rounds`：录制的运行准确显示了你的服务器做了什么。
- 选择一个包含保留轮次、纠正轮次和第一次猜测失败轮次的种子，使三种判定结果都会出现。

**避免**

- 同一屏幕上放置多张正在播放的卡片。每张卡片在播放时都会逐帧重绘。
- 单词前面没有空格的 token。答案中的词会连在一起，而标点规则依赖于空格。
- 用计时器更改 token 或种子。每次更改都会重新计划运行，并从头开始。
- 把 `Stats` 当作你系统的测量值。它描述的是卡片上的运行。

### 常见问题

**为什么加速比低于每次前向计算的 token 数？** 加速比计入了草稿模型的时间：每个被草拟的 token 花费 `DraftCost` 个前向计算的时间。6 次前向计算加上 24 个被草拟的 token，使这次运行需要 6 + 2.4 = 8.4 次前向计算来写出 22 个 token，即快 2.6 倍；而每次前向计算的 token 数为 22 / 6 = 3.7。

**为什么最后一轮从不草拟最后一个 token？** 目标每轮至少写出一个 token，因此计划会把答案的最后一个 token 留给目标。当只剩一个 token 时，该轮根本没有草稿。

**为什么被拒绝的猜测之后的标签块显示的是正确的词？** 一旦某个猜测被拒绝，其后的所有内容都会在未经核对的情况下被丢弃，因此这些标签块显示真实的 token，并逐渐淡出。

**如何得到与截图相同的运行？** 保持 token、种子和草稿长度不变。计划不依赖其他任何东西。

**能否隐藏播放按钮？** 将 `AreControlsVisible` 设为 false。运行仍会自行播放，并可以通过 `IsPlaying`、`Play()` 和 `Restart()` 来驱动。

| 属性 | 类型 | 含义 |
|---|---|---|
| `Passes` | `int` | 目标前向计算次数，每轮一次 |
| `Drafted` | `int` | 草稿提出的 token 数 |
| `Accepted` | `int` | 被目标接受的草稿 token 数 |
| `Tokens` | `int` | 写入答案的 token 数 |

| `TokensPerPass` | `double` | tokens / passes |
| `Speedup` | `double` | tokens / (passes + draft cost × drafted) |

## 无障碍

- 卡片是一个有名称的分组：其无障碍名称为 `Title`。
- 通道对辅助技术隐藏。一轮的判定结果出现后，会有一段隐藏文字概括该轮：草稿提出了什么、目标保留了几个猜测，以及它改为写出了哪个 token（或额外添加了哪个）。
- 每条答案行都以目前已写出的文字作为其无障碍名称（“Output: Tomorrow at 7, the east”），因此屏幕阅读器朗读的是词，而不是 token。
- 每个统计数据都有一个朗读值（“Speedup: 2.6 times”、“Drafts accepted: 67 percent”，第一轮之前为“not yet”）；滚动的数字则是装饰性的。
- 判定结果从不只依赖颜色：被保留的猜测获得勾号，被拒绝的猜测被划掉并在目标的 token 旁标上叉号，被丢弃的猜测淡出。
- 一个礼貌的实时区域会播报播放、暂停、重新开始、比较的开启或关闭、新的草稿长度及其预期接受率和加速比，以及结束时的结果。它从不播报每一轮。
- 指针聚焦时不绘制焦点环；键盘焦点则显示共享的焦点环。

## 动效

- 草稿标签块逐个出现，从左侧 4 px 处淡入；在等待目标时，一道柔和的闪光掠过它们的文字。
- 目标的扫过动作从左到右填充单元格；每个判定结果在扫过单元格中点时淡入，划线从左侧开始绘制。
- 被保留的猜测和目标的 token 以临界阻尼弹簧从标签块飞入答案的位置，间隔 20 ms，同时各列淡出；它们的下划线会在落定后不久采用模型的颜色。
- 通道随换行的列以平滑弹簧伸展，仅目标行也以同一弹簧展开和收起。统计数据逐位滚动。
- 状态文字与行名称以短暂的交叉淡化切换。

| 变化 | 完整 | 减弱 | 关闭 |
|---|---|---|---|
| 自动播放 | 卡片大部分可见时 | 从不；等待播放 | 从不；等待播放 |
| 标签块与各列 | 从 4 px 处滑入，等待时闪光 | 原位出现，没有闪光 | 原位出现 |
| 扫过动作 | 连续填充每个单元格 | 在判定时整格前进 | 整格前进 |
| token 进入答案 | 以弹簧飞入，然后淡入下划线 | 原位淡入 | 原位淡入 |
| 通道与仅目标行 | 以弹簧伸缩 | 直接跳到其尺寸 | 直接跳到其尺寸 |
| 统计数据 | 逐位滚动 | 立即变化 | 立即变化 |

## 相关组件

- `MixtureOfExperts`：一次前向计算内部发生的事：路由器把每个 token 发送给其前 k 个专家。
- `PromptCache`：另一种节省时间的方式：共享的提示前缀从缓存中读取。
- `AgentLoop` 和 `ReasoningTree`：其他具有相同播放控件的 AI 讲解插图。

| 组件 | 适用场景 |
|---|---|
| `MarkdownStream` | 你要向读者流式显示一个回答 |
| `MixtureOfExperts` | 故事是模型如何在一次前向计算内部为每个 token 路由 |
| `PromptCache` | 故事是重复的提示如何变得更便宜 |
| `LineChart` | 你要绘制真实的延迟或吞吐量测量值 |
