## 何時使用

`SpeculativeDecoding` 說明為什麼語言模型在小型草稿模型先行推測時，能回答得更快。草稿通道每次提出幾個 token，以虛線「ghost」標籤塊呈現；目標通道以一次前向運算檢查所有這些 token；目標同意的猜測會進入答案。卡片會依回合播放整個執行過程一次，並保留累計統計：與只用目標模型相比，答案寫得快了多少、草稿被接受的比例，以及每次目標前向運算寫出的 token 數。它是講解插圖，不是解碼器：數字僅供示意。

- **關於延遲的模型與產品頁面**：寫著「responses are up to 2.5 times faster」的頁面，可以展示時間花在哪裡。讀者會看到大型模型的每一次前向運算都能寫出數個 token，而不是一個。
- **推論儀表板與版本說明**：用 `Rounds` 重播從自家伺服器錄製的執行，可以把真實請求的接受率與每次前向運算的 token 數，和彙整數千次請求的指標並排呈現。
- **講授草稿長度的取捨**：滑桿讓讀者嘗試 2 到 8 個 token 的草稿。草稿較長時，猜中的情況下每次前向運算寫得更多，但接受的比例較小，因為第一次失誤之後的內容都會被丟棄。使用內建範例時，加速比在 4 時達到高峰。
- **與一般解碼比較**：比較開關會在同一時鐘上並排另一條線，其中目標模型每次前向運算只寫一個 token，因此兩種做法的差距是看得見的，而不只是文字說明。
- **課程與部落格文章**：執行過程是確定性的。相同的 token、種子與草稿長度永遠產生相同的回合，因此截圖或提到「第 3 回合」的段落會一直正確。

## 何時不用

- **向使用者串流真實回答**：使用 `MarkdownStream` 或聊天元件。此卡片說明速度背後的機制，並不會隨文字抵達逐步顯示。
- **Token 機率與候選項目**：顯示某個位置的候選項目與其分數的卡片是另一回事。這裡的草稿模型只會猜對或猜錯，不帶任何機率。
- **在模型之間路由請求**：推測解碼每個請求都會同時執行兩個模型。若要說明哪個模型回答哪個請求，請使用路由器的示意圖。
- **單次前向運算內部發生的事**：注意力與專家路由低於此卡片的層級。模型內部的路由請使用 `MixtureOfExperts`。
- **即時效能監控**：統計數字是由卡片上的執行計算出來的，而不是來自你的流量。要做到這一點，請使用以自身測量值繪製的圖表。

## 用法

此卡片不需要資料。未設定任何內容時，它會播放內建範例：一段 22 個 token 的維護通知，以每次 4 個 token 的草稿推測，需要 6 次目標前向運算，結果比單獨使用目標模型快 2.6 倍。

```xml
<arc:SpeculativeDecoding />
```

`SpeculativeDecoding` 衍生自 `Explainer`，也就是動畫 AI 講解插圖的基底類別；`Explainer` 再衍生自 Avalonia 的 `TemplatedControl`。基底類別提供場景時鐘、播放與重新開始按鈕及其名稱、自動播放與即時區域；此控制項則描述各通道、答案與計算方式。

### 你自己的答案

`Tokens` 接受目標模型寫出的答案，每個 token 對應一個 `DecodeToken`。文字保留前導空白，與分詞器一致（`" refund"`）；沒有前導空白的 token，例如標點符號，會接在前一個字之後。`Ease` 表示草稿猜中該 token 的可能性（0 到 1；未設定時使用 0.9），`Miss` 則是草稿猜錯時提出的內容。數字、名稱與罕見字應設定較低的 ease，並給出看似合理的 miss；簡短的功能字與標點則保持容易猜中。若頁面需要，通道名稱可以使用虛構的模型名稱。

<Demo name="OwnAnswer" />

`Seed` 決定哪些猜測會成功。每次猜測都從種子產生器抽取一個數字，數字小於該 token 的 ease 時即成功；抽取會在第一次失誤時停止。請調整種子，直到執行過程呈現你想要的故事，然後保留它：相同的種子、token 與草稿長度永遠重播相同的回合。`TokensSource` 則改為接受一個 token 序列，供資料繫結使用。

### 錄製的執行

`Rounds`（或 `RoundsSource`）會重播從你自己的伺服器錄製的執行，而不是模擬一次。每個 `DecodeRound` 包含草稿所提出的 token、目標從頭開始接受了其中幾個，以及目標自己寫出的 token：第一個被拒絕之猜測的更正，或是所有猜測都被接受時的獎勵 token。答案即為被接受的草稿加上目標的 token，依順序排列。草稿長度滑桿會被隱藏，因為回合本身已經固定了草稿長度。

### 結構

1. **標頭**：標題（`Title`，同時也是卡片的無障礙名稱）、說明目前步驟的狀態行，以及播放／暫停與重新開始按鈕。狀態行在窄卡片上會換行，並在那裡保留兩行的空間，因此通道不會移動。
2. **草稿通道**（`DraftLabel`、`DraftDetail`）：代表小型模型的小圓點。每個回合的標籤塊會以草稿顏色的虛線 ghost 標籤塊一個接一個出現，等待時帶有柔和的閃光。
3. **目標通道**（`TargetLabel`、`TargetDetail`）：代表大型模型的大圓點。每個標籤塊下方都有一個儲存格，由目標的掃描從左到右填滿。被接受的猜測會出現勾號；第一個被拒絕的猜測會以叉號劃掉，並顯示目標自己的 token，其後的猜測則淡出。若所有猜測都被接受，會多出一個帶加號的儲存格，放入目標的獎勵 token。
4. **答案行**（"Output"，比較時為 "Speculative"）：整句話從一開始就排好版，因此該行不會重新排列。Token 會落在各自的位置上，並以寫出它的模型顏色加上底線：被接受的猜測使用草稿顏色，目標自己的 token 使用目標顏色。前向運算次數顯示在名稱下方，結束時會出現勾號。
5. **僅目標行**（`IsComparing`）：同一句話以目標模型每次前向運算寫一個 token 的方式，在同一時鐘上寫出，並以目標顏色加上底線。
6. **統計**：加速比、草稿被接受的比例，以及每次前向運算的 token 數。在第一個回合結算前顯示破折號，之後每回合結束時滾動更新為累計總數。
7. **控制項**：草稿長度滑桿（2 到 8）與比較開關。
8. **摘要**：結束時，通道旁會以兩行顯示總計。

### 故事及其計算

每個回合有三個步驟。預設值下（每次前向運算 640 ms，草稿成本 0.1）：

| 步驟 | 持續時間 | 發生的事 |
|---|---|---|
| 草稿 | k × 64 ms | 草稿每 64 ms 提出一個標籤塊，共提出 k 個。k 為草稿長度，但上限為剩餘 token 數減一，因此目標總會寫出最後一個 token。 |
| 驗證 | 0.72 次前向運算（461 ms） | 掃描以 0.4 次前向運算（256 ms，與儲存格數量無關）跨過全部 k 個儲存格。掃描經過每個儲存格的中點時，會給出該儲存格的判定。 |
| 結算 | 0.28 次前向運算（179 ms） | 被保留的猜測與目標的 token 以 20 ms 的間隔飛入答案，各欄淡出，統計數字滾動更新。 |

因此一個回合會寫出 a 個被接受的猜測，加上目標的一個 token，成本為一次前向運算加上草稿時間。統計數字由目前為止各回合的總計推算：

- **加速比** = tokens /（passes + draft cost × drafted）。草稿時間也計算在內，因此多草稿並非免費。
- **草稿接受比例** = accepted / drafted，以整數百分比表示。
- **每次前向運算的 token 數** = tokens / passes。單獨的目標模型恰好寫出一個。

內建範例呈現了讀者應當帶走的形狀。加速比從短草稿起升，到草稿長度 4 時達到高峰後下降，而被接受的草稿比例則持續下降：

| 草稿長度 | 前向運算次數 | 已草稿 | 已接受 | 接受比例 | 加速比 |
|---|---|---|---|---|---|
| 2 | 10 | 19 | 12 | 63% | 1.8× |
| 3 | 8 | 21 | 14 | 67% | 2.2× |
| 4 | 6 | 24 | 16 | 67% | 2.6× |
| 5 | 6 | 29 | 16 | 55% | 2.5× |
| 6 | 6 | 33 | 16 | 48% | 2.4× |
| 8 | 6 | 39 | 16 | 41% | 2.2× |

`PlannedStats` 會在執行規劃完成時立即提供整個執行的總計，`Stats` 提供目前為止已結算回合的總計，`Completed` 則在投機線完成時回報總計。`DraftCost` 設定每個草稿 token 的成本，以前向運算的比例表示，同時影響畫面與加速比；`PassDuration` 則設定一次前向運算在畫面上花費的時間。

### 與單獨的目標模型比較

`IsComparing` 會開啟僅目標行。它在與投機線相同的時鐘上，於 (m − 1) 次前向運算 + 0.72 次前向運算的時刻寫出第 m 個 token，因此內建範例的六次前向運算之後，單獨的目標模型已寫出 22 個 token 中的 8 個。投機線結束後，故事會繼續進行，直到單獨的目標模型也完成，此時狀態行會說明這一點。在執行結束後才開啟比較，會從當時的時間點接續，而不會重新開始執行。統計數字與 `Completed` 一律描述投機線。

### 播放

執行只播放一次，即卡片大部分進入可視範圍時的第一次（`AutoPlay`），結束時停止；`IsLooping` 則會在幾秒後再次播放。播放按鈕會在停止的位置暫停與繼續執行；結束後按下則從頭播放。重新開始一律從頭播放。`IsPlaying` 為雙向，`Play()`、`Pause()` 與 `Restart()` 可在程式碼中執行相同的操作。`Speed` 縮放時鐘；卡片上沒有速度控制，也沒有單步按鈕。

變更草稿長度（透過滑桿或 `DraftLength`）會重新規劃執行，並從頭播放。新的 token、回合、種子、草稿成本或前向運算時間也是如此。與舊值相等的輸入，例如內容相同的新清單，不會重新開始執行。

```xml
<arc:SpeculativeDecoding DraftLength="{Binding DraftLength}"
                         IsComparing="{Binding ShowsBaseline}" />
```

```csharp
decoder.Completed += (_, e) => status.Text = $"{e.Stats.Speedup:0.0}× faster in {e.Stats.Passes} passes";
decoder.DraftLength = 6;
decoder.Restart();
```

### 載入與錯誤

`Status` 描述錄製執行背後的資料。當其為 `Loading` 時，通道會變暗，狀態行顯示旋轉指示器與閃爍的標籤，控制項停用，執行等待；狀態變為 `Ready` 後才開始自動播放。`Error` 會以危險圖示顯示 `ErrorText`（或預設訊息）。只有在有人處理 `RetryRequested`，或設定了 `RetryCommand` 時，播放按鈕旁才會出現重試按鈕，因為按下沒有作用的按鈕比沒有按鈕更糟。

在減少動態效果下，卡片永遠不會自行開始，也不會跳到結尾：它會停在第一個狀態，直到讀者按下播放。執行仍有完全相同的節拍，但標籤塊出現時不滑動，掃描一次前進整個儲存格，劃線立即畫出，沒有閃光，token 則在答案中原位淡入，而非飛入。

### 內容指引

撰寫 15 到 30 個 token 的答案，且單獨閱讀也通順；並依真實模型的實際情況，混合容易與困難的 token：功能字與標點容易，數字、名稱與關鍵名詞困難。每次失誤都應是同類型、合理的錯誤猜測（不同的數字、相近的字），而非隨機的字。通道名稱保持通用，或使用明顯虛構的名稱；除非執行真的來自該產品，否則不要寫出真實的產品名稱。

| 不要寫 | 改為 |
|---|---|
| 一句 60 個 token 的句子 | 一或兩個短句，每句 15 到 30 個 token |
| 每個 token 的 ease 都是 0.5 | 容易的 token 接近 0.95，困難的接近 0.1 到 0.3 |
| 數字卻用 `Miss=" banana"` | 用 `Miss=" 30"` 對應 `" 25"` |
| 模擬執行上使用真實的模型名稱 | 「Draft model」與「Target model」，或虛構的名稱 |
| 模擬執行旁的頁面文字寫「快 3×」 | 「在這個示意執行中大約快 2.6 倍」 |

### 最佳實務

**建議**

- 模擬執行時說明數字僅供示意；錄製的執行則說明其來源。
- 範例保持預設草稿長度 4，讓第一次執行呈現最佳加速比，而滑桿能在兩個方向上展示取捨。
- 需要引用的數字請使用 `Rounds`：錄製的執行準確顯示伺服器的實際結果。
- 選擇一個其執行包含一個被接受的回合、一個被更正的回合，以及一個第一次猜測即失敗的回合的種子，使三種判定都會出現。

**避免**

- 同一畫面上放置多張播放中的卡片。每張卡片都會在播放時逐影格繪製。
- 單字的 token 缺少前導空白。答案會把字連在一起，而標點的規則依賴空白。
- 以計時器變更 token 或種子。每次變更都會重新規劃執行，並從頭開始。
- 把 `Stats` 當作你系統的測量值。它描述的是卡片上的執行。

### 常見問題

**為什麼加速比低於每次前向運算的 token 數？** 加速比會計入草稿模型的時間：每個草稿 token 的成本為一次前向運算的 `DraftCost`。以 6 次前向運算與 24 個草稿 token 來計算，這次執行為 22 個 token 花費 6 + 2.4 = 8.4 次前向運算，也就是快 2.6 倍，而每次前向運算的 token 數為 22 / 6 = 3.7。

**為什麼最後一個回合從不草稿最後一個 token？** 目標每回合至少會寫出一個 token，因此規劃會把答案的最後一個 token 留給目標。只剩一個 token 的回合完全沒有草稿。

**為什麼被拒絕的猜測之後的標籤塊會顯示正確的字？** 一旦猜測被拒絕，其後的所有內容都會在未經檢查的情況下被丟棄，因此那些標籤塊會顯示真實的 token 並淡出。

**如何取得與截圖相同的執行？** 保持 token、種子與草稿長度不變。規劃不依賴其他任何東西。

**能否隱藏播放按鈕？** 將 `AreControlsVisible` 設為 false。執行仍會自行播放，也可以用 `IsPlaying`、`Play()` 與 `Restart()` 控制。

| 屬性 | 類型 | 意義 |

總計使用 `DecodeStats` 記錄，也是 `SpeculativeDecodingCompletedEventArgs` 的 `Stats` 屬性。

| 屬性 | 類型 | 意義 |
|---|---|---|
| `Passes` | `int` | 目標的前向運算次數，每個回合一次 |
| `Drafted` | `int` | 草稿提出的 token 數 |
| `Accepted` | `int` | 目標接受的草稿 token 數 |
| `Tokens` | `int` | 寫入答案的 token 數 |

## 無障礙

- 此卡片是具名群組：其無障礙名稱為 `Title`。
- 通道對輔助技術隱藏。一旦某個回合有了判定，隱藏的文字會摘要它：草稿提出了什麼、目標保留了幾個猜測，以及它改寫成了哪個 token（或新增了哪個）。
- 每條答案行都帶有目前已寫出文字的無障礙名稱（"Output: Tomorrow at 7, the east"），讓螢幕閱讀器朗讀單字而非 token。
- 每個統計數字都有可朗讀的數值（"Speedup: 2.6 times"、"Drafts accepted: 67 percent"，首個回合之前為 "not yet"）；滾動的數字僅為裝飾。
- 判定從不只依賴顏色：被保留的猜測會有勾號，被拒絕的猜測會以叉號劃掉並緊鄰目標的 token，被丟棄的猜測則淡出。
- 一個禮貌的即時區域會播報播放、暫停、重新開始、比較開啟或關閉、新的草稿長度及其預期接受率與加速比，以及結束時的結果。它從不播報每個回合。
- 指標焦點不顯示外框；鍵盤焦點則顯示共用的焦點環。

### 鍵盤

| 按鍵 | 操作 |
|---|---|
| `Tab` / `Shift+Tab` | 在播放或暫停、重新開始、草稿長度滑桿與比較開關之間移動 |
| `Enter`、`Space` | 在播放或暫停與重新開始上：啟動；在比較開關上：切換比較 |
| `Left` / `Down`、`Right` / `Up` | 在滑桿上：將草稿縮短或加長一個 token；執行重新播放 |
| `Home`、`End` | 在滑桿上：跳到 2 或 8 個 token 的草稿 |

## 動態效果

- 草稿標籤塊一個接一個出現，從左側 4 px 處淡入；等待目標時，柔和的閃光會掠過它們的文字。
- 目標的掃描從左到右填滿儲存格；每個判定在掃描到達儲存格中點時淡入，劃線則從左側開始畫出。
- 被保留的猜測與目標的 token 以臨界阻尼彈簧從標籤塊飛入答案的位置，間隔 20 ms，同時各欄淡出；它們的底線在落定後不久變為該模型的顏色。
- 通道隨換行的欄位以平滑彈簧移動，僅目標行以同一彈簧開啟與關閉。統計數字逐位滾動。
- 狀態行與行名稱以短暫的淡入淡出交替切換。

| 變化 | 完整 | 減少 | 關閉 |
|---|---|---|---|
| 自動播放 | 卡片大部分進入可視範圍時 | 從不；等待播放 | 從不；等待播放 |
| 標籤塊與欄 | 從 4 px 處滑入，等待時閃光 | 原位出現，無閃光 | 原位出現 |
| 掃描 | 持續填滿各儲存格 | 在判定時整格前進 | 整格前進 |
| token 進入答案 | 以彈簧飛入，然後淡入底線 | 原位淡入 | 原位淡入 |
| 通道與僅目標行 | 以彈簧增長與縮小 | 直接跳到其大小 | 直接跳到其大小 |
| 統計數字 | 逐位滾動 | 立即變更 | 立即變更 |

## 相關

- `MixtureOfExperts`：單次前向運算內部發生的事，路由器會把每個 token 送往得分最高的前幾名專家。
- `PromptCache`：另一種節省時間的方式，共用的提示前綴會從提示快取中讀取。
- `AgentLoop` 與 `ReasoningTree`：其他具有相同播放控制項的 AI 講解插圖。

| 元件 | 適用時機 |
|---|---|
| `MarkdownStream` | 你要向讀者串流顯示一則回答 |
| `MixtureOfExperts` | 故事是模型如何在單次前向運算中為每個 token 路由 |
| `PromptCache` | 故事是重複的提示如何變得更便宜 |
| `LineChart` | 你要繪製真實的延遲或吞吐量測量值 |
